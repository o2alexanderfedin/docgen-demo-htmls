Backup Strategy

The LLM Gateway implements a comprehensive backup strategy to protect all critical data and configurations.

Backup Components

The following components are included in the backup strategy:

Component Data Type Backup Method Frequency Retention
PostgreSQL Database Structured data Automated snapshots Daily full, 5-minute WAL 30 days
Redis Cache Cache data RDB snapshots Every 6 hours 7 days
Configuration Kubernetes configs GitOps repository On change Indefinite
Infrastructure Terraform state S3 + versioning On change Indefinite
Prompt Templates Business data Database + separate export Daily 90 days
Logs Operational data S3 archival Streaming 90 days
Metrics Time-series data S3 long-term storage Daily aggregation 1 year

Database Backup Strategy

Database backups follow a multi-layered approach:

  1. Automated RDS Snapshots:
  2. Daily full database snapshots
  3. Retained for 30 days

  4. Encrypted at rest

  5. Point-in-Time Recovery:

  6. Transaction logs (WAL) archived every 5 minutes
  7. Allows recovery to any point in the last 30 days

  8. Automated verification of recovery capability

  9. Cross-Region Backup Replication:

  10. Snapshots replicated to DR region
  11. Scheduled with 1-hour delay
  12. Regular validation of replica integrity

Configuration Backup

All configuration is stored in version control:

  1. GitOps Repository:
  2. All Kubernetes manifests
  3. Helm chart values
  4. Application configurations

  5. Deployment specifications

  6. Infrastructure as Code:

  7. Terraform state files in S3 with versioning
  8. Terraform code in Git repository

  9. AWS CloudFormation templates (when used)

  10. Secrets Backup:

  11. AWS Secrets Manager automatic replication
  12. Encryption key backups in AWS KMS

Failure Scenarios

The DR plan addresses the following failure scenarios:

Scenario Impact Recovery Approach RTO RPO
Single AZ Failure Partial service degradation Auto-scaling across remaining AZs < 5 minutes 0
Database Failure Potential data access disruption Automatic failover to standby < 5 minutes < 1 minute
Full Region Failure Complete service outage Cross-region failover < 4 hours < 15 minutes
Data Corruption Data integrity issues Point-in-time recovery < 1 hour Depends on detection
Malicious Attack Security breach Isolation and clean recovery < 8 hours Depends on detection
Provider Outage Service degradation Multi-provider failover < 10 minutes 0

Recovery Procedures

Regional Failover Procedure

When to use: Complete primary region failure

sequenceDiagram
    participant Ops as Operations Team
    participant DNS as Route 53
    participant DR as DR Environment
    participant Backup as Backup Systems

    Note over Ops: Primary Region Failure Detected

    Ops->>Ops: Declare Disaster
    Ops->>DR: Verify DR Environment Readiness
    Ops->>DR: Scale Up DR Environment

    par Database Recovery
        Ops->>DR: Promote DB Replica to Primary
    and Configuration Deployment
        Ops->>DR: Deploy Current Configurations
    end

    Ops->>Ops: Perform Health Checks
    Ops->>DNS: Update DNS to Point to DR Region
    Ops->>DR: Verify Application Functionality

    Note over Ops: Service Restored in DR Region

    Ops->>Backup: Begin Reconstruction of Primary Region

Detailed Steps:

  1. Declare Disaster Event
  2. Incident commander declares DR event
  3. Notify stakeholders of service disruption

  4. Assemble recovery team

  5. Activate DR Environment bash # Scale up DR environment aws autoscaling update-auto-scaling-group \ --auto-scaling-group-name llm-gateway-dr-workers \ --min-size 9 \ --max-size 18 \ --desired-capacity 9

  6. Promote Database Replica bash # Promote RDS read replica to primary aws rds promote-read-replica \ --db-instance-identifier llm-gateway-dr-db

  7. Deploy Current Configurations bash # Apply latest configuration kubectl apply -f kubernetes/dr-deployment/ --context dr-cluster

  8. Verify DR Environment Health bash # Perform health checks for service in api-service execution-service prompt-service cache-service; do kubectl exec -it $(kubectl get pods -l app=$service -o jsonpath='{.items[0].metadata.name}' --context dr-cluster) --context dr-cluster -- curl localhost:8080/health/deep done

  9. Update DNS bash # Switch DNS to DR environment aws route53 change-resource-record-sets \ --hosted-zone-id $HOSTED_ZONE_ID \ --change-batch file://dns/failover-to-dr.json

  10. Verify Application Functionality bash # Run synthetic transactions ./scripts/run-dr-validation-tests.sh

  11. Begin Primary Region Recovery

  12. Assess primary region status
  13. Begin rebuilding primary environment
  14. Plan for failback when ready

Database Recovery Procedure

When to use: Database corruption or failure

flowchart TD
    Start([Database Issue Detected]) --> Assess[Assess Impact & Type]
    Assess --> Decision{Corruption or Failure?}

    Decision -- Failure --> Failover[Initiate RDS Failover]
    Failover --> VerifyFailover[Verify Failover Success]
    VerifyFailover --> RecoverConnections[Recover Application Connections]

    Decision -- Corruption --> TimePoint[Determine Recovery Point]
    TimePoint --> PITR[Initiate Point-in-Time Recovery]
    PITR --> CreateNew[Create New DB Instance]
    CreateNew --> ValidateData[Validate Recovered Data]
    ValidateData --> SwitchOver[Switch Applications to New DB]

    RecoverConnections --> Complete([Recovery Complete])
    SwitchOver --> Complete

Detailed Steps for Corruption Recovery:

  1. Isolate the Issue
  2. Identify affected data
  3. Document corruption timeline

  4. Take database snapshot before recovery

  5. Determine Recovery Point ```bash # List available recovery points aws rds describe-db-snapshots \ --db-instance-identifier llm-gateway-db

# List automated backups with recovery time aws rds describe-db-instance-automated-backups \ --db-instance-identifier llm-gateway-db ```

  1. Initiate Point-in-Time Recovery bash # Restore to point in time before corruption aws rds restore-db-instance-to-point-in-time \ --source-db-instance-identifier llm-gateway-db \ --target-db-instance-identifier llm-gateway-db-recovered \ --restore-time 2023-05-15T04:00:00Z

  2. Validate Recovered Data bash # Connect to new instance and verify data PGPASSWORD=$DB_PASSWORD psql -h llm-gateway-db-recovered.example.us-east-1.rds.amazonaws.com -U admin -c "SELECT count(*) FROM prompts WHERE updated_at > '2023-05-14';"

  3. Prepare for Switchover bash # Scale down application to minimize disruption kubectl scale deployment api-service execution-service prompt-service --replicas=1 -n llm-gateway

  4. Update Database Connection ```bash # Update connection secret aws secretsmanager update-secret \ --secret-id llm-gateway/database/credentials \ --secret-string "{\"host\":\"llm-gateway-db-recovered.example.us-east-1.rds.amazonaws.com\",\"username\":\"$DB_USER\",\"password\":\"$DB_PASSWORD\"}"

# Restart services to pick up new connection kubectl rollout restart deployment api-service execution-service prompt-service -n llm-gateway ```

  1. Verify and Scale Up ```bash # Verify applications are working with recovered data curl -X GET https://api.example.com/health/deep

# Scale back to normal operation kubectl scale deployment api-service --replicas=6 execution-service --replicas=12 prompt-service --replicas=4 -n llm-gateway ```

Testing Schedule

The following tests are performed regularly:

Test Type Frequency Components Duration Impact
Tabletop Exercise Monthly Recovery procedures, Team readiness 2 hours None
Component Tests Quarterly Database recovery, Application restore 4 hours None (isolated environment)
DR Simulation Semi-annually Full region failover 8 hours Minimal (during maintenance window)
Backup Verification Daily Automated backup verification Automated None
Chaos Engineering Monthly Resilience verification 4 hours Minimal (isolated components)

DR Test Procedure

Each DR test follows a standardized process:

  1. Test Planning
  2. Define test objectives and success criteria
  3. Create detailed test plan and schedule

  4. Identify participants and responsibilities

  5. Pre-Test Preparation

  6. Review and update recovery procedures
  7. Verify backup integrity

  8. Prepare test environment

  9. Test Execution

  10. Follow documented recovery procedures
  11. Document all actions and outcomes

  12. Measure recovery times

  13. Test Evaluation

  14. Assess whether RTO and RPO were met
  15. Identify issues and bottlenecks

  16. Document lessons learned

  17. Improvement Implementation

  18. Update recovery procedures
  19. Address identified issues
  20. Implement process improvements

Recovery Time Objectives

The LLM Gateway has defined the following recovery objectives:

Scenario RTO (Recovery Time Objective) RPO (Recovery Point Objective)
Single AZ Failure < 5 minutes 0 (no data loss)
Database Primary Failure < 5 minutes < 1 minute
Cache Failure < 5 minutes 0 (reconstructible from database)
Full Region Failure < 4 hours < 15 minutes
Data Corruption < 1 hour Depends on detection time
Multi-Region Failure < 24 hours < 1 hour

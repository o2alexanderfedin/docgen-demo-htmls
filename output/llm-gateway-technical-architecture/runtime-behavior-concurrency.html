Introduction

This document describes the runtime behavior and concurrency model of the LLM Gateway, explaining how requests are processed, how concurrency is managed, and how the system handles high load scenarios. The LLM Gateway processes a mix of synchronous and streaming requests with varying latency requirements, necessitating careful design of its runtime architecture.

Request Processing Lifecycle

Synchronous Request Handling

This sequence diagram illustrates the lifecycle of a typical synchronous request through the system:

Lifecycle Steps:

  1. Request Reception: Client submits an HTTP or gRPC request
  2. Authentication & Validation: Request is authenticated and validated
  3. Execution Delegation: Request is passed to the execution manager
  4. Cache Check: System checks if an identical request exists in cache
  5. Provider Selection: If cache miss, appropriate provider client is selected
  6. LLM Request: The request is sent to the LLM provider
  7. Response Processing: Provider response is processed and normalized
  8. Caching: Response is cached if cacheable
  9. Metric Recording: Usage metrics are recorded
  10. Response Delivery: Formatted response is returned to client

Streaming Request Handling

Streaming requests follow a similar but distinct pattern:

Streaming Lifecycle Steps:

  1. Request Reception: Client submits a streaming request
  2. Stream Initialization: Response emitter is created for the client connection
  3. Execution Delegation: Streaming execution is initiated with callback handler
  4. Provider Selection: Appropriate provider client is selected
  5. Streaming Request: Streaming connection is established with LLM provider
  6. Token Processing: Each token is processed and emitted to the client as received
  7. Stream Completion: Upon completion, metrics are recorded and connection is closed

Concurrency Model

The LLM Gateway implements a hybrid concurrency model combining thread pools for CPU-bound work and asynchronous processing for I/O-bound operations.

Thread Pool Architecture

Thread Pool Components:

  1. Request Worker Pool
  2. Size: min(32, num_cores * 2)
  3. Purpose: Initial request handling and routing

  4. Configuration: Fixed size with small queue

  5. Compute Thread Pool

  6. Size: num_cores * 4
  7. Purpose: CPU-intensive operations (validation, transformation)

  8. Configuration: Work-stealing pool with bounded queue

  9. I/O Thread Pool

  10. Size: Elastic (16-128 threads)
  11. Purpose: I/O-bound operations (network, database)

  12. Configuration: Cached thread pool with timeout

  13. Streaming Thread Pool

  14. Size: Elastic (8-64 threads)
  15. Purpose: Managing streaming connections
  16. Configuration: Virtual threads (Java 19+) or cached thread pool

Asynchronous Processing

The system uses the CompletableFuture API for asynchronous processing:

// Example of async execution flow in ExecutionManagerImpl
public CompletableFuture<LLMFetchAnswerResponseDTO> executeAsync(LLMFetchAnswerRequestDTO request) {
    return CompletableFuture
        .supplyAsync(() -> validateRequest(request), computeExecutor)
        .thenComposeAsync(this::checkCache, ioExecutor)
        .thenComposeAsync(result -> {
            if (result.isPresent()) {
                return CompletableFuture.completedFuture(result.get());
            } else {
                return executeWithProvider(request);
            }
        }, ioExecutor)
        .thenApplyAsync(this::postProcessResponse, computeExecutor)
        .whenCompleteAsync((response, error) -> {
            if (error == null) {
                recordMetrics(request, response);
            } else {
                recordError(request, error);
            }
        }, computeExecutor);
}

Key Async Patterns:

  • Task submission to appropriate thread pools based on operation type
  • Asynchronous composition of dependent operations
  • Non-blocking I/O for external service calls
  • Parallel execution of independent operations

Throttling and Backpressure

The system implements several mechanisms for throttling and backpressure:

Throttling Components:

  1. API Rate Limiter
  2. Configured per tenant and API key
  3. Implements token bucket algorithm

  4. Customizable bucket size and refill rate

  5. Concurrency Semaphores

  6. Limit parallel requests to each provider
  7. Prevent provider quota exhaustion

  8. Dynamically adjustable based on provider health

  9. Request Queuing

  10. Queue for requests that exceed concurrency limits
  11. Time-based eviction for queued requests

  12. Priority based on client tier

  13. Adaptive Retry

  14. Exponential backoff for rate-limited requests
  15. Circuit breaking for failing providers
  16. Per-provider retry configuration

Event-Driven Components

The LLM Gateway includes several event-driven components for non-request processing:

Event-Driven Components:

  1. Event Bus
  2. Implementation: In-memory message bus
  3. Event types: Request, Response, Error, Config Change

  4. Dispatcher: Single-threaded with overflow protection

  5. Analytics Consumer

  6. Purpose: Process usage metrics
  7. Processing model: Batched processing

  8. Throughput: High-throughput, low latency

  9. Audit Consumer

  10. Purpose: Record audit events
  11. Processing model: Reliable delivery

  12. Storage: Persistent audit log

  13. Cache Invalidation Consumer

  14. Purpose: Invalidate affected cache entries
  15. Processing model: Immediate processing
  16. Scope: Targeted invalidation

State Management

The LLM Gateway uses different state management approaches for different components:

  1. Request State
  2. Stateless request processing
  3. No session state between requests

  4. Request context passed through execution chain

  5. Configuration State

  6. Cached configuration loaded at startup
  7. Dynamic reconfiguration via admin APIs

  8. Configuration changes broadcast via events

  9. Connection State

  10. Connection pooling for provider clients
  11. Keep-alive for persistent connections

  12. Circuit breaking for failed connections

  13. Streaming State

  14. Per-request state for streaming responses
  15. Token buffer for efficient streaming
  16. Stream timeout monitoring

Transaction Handling

The system implements transaction handling for data consistency:

  1. Database Transactions
  2. Transaction boundaries defined at service layer
  3. Optimistic locking for concurrent updates

  4. Read-committed isolation level

  5. Distributed Operations

  6. Eventual consistency for distributed operations
  7. Idempotent operations where possible

  8. Compensating transactions for failures

  9. Error Handling in Transactions

  10. Automatic rollback on exceptions
  11. Detailed transaction logging
  12. Recovery mechanisms for partial failures

Timeouts and Circuit Breaking

The LLM Gateway implements a comprehensive timeout and circuit breaking strategy:

Timeout Configuration:

  1. Connection Timeouts
  2. HTTP connection establishment: 5 seconds
  3. Socket read timeout: 30-120 seconds (model dependent)

  4. Socket write timeout: 5 seconds

  5. Request Timeouts

  6. Default request timeout: 60 seconds
  7. Streaming initial response: 10 seconds
  8. Streaming token timeout: 5 seconds

  9. Configurable per request and provider

  10. Queue Timeouts

  11. Queue wait time: 30 seconds
  12. Processing time: Model-dependent
  13. Client connection idle timeout: 120 seconds

Circuit Breaker Configuration:

  1. Failure Thresholds
  2. Error threshold: 50% of requests in 1-minute window
  3. Minimum requests: 5 requests in window

  4. Tracked errors: Timeouts, 5xx responses, connection errors

  5. Recovery Strategy

  6. Open circuit duration: 30 seconds
  7. Half-open test requests: 5 requests
  8. Success threshold: 3 consecutive successes
  9. Backoff multiplier: 1.5x (up to 5 minutes)

Resource Management

The LLM Gateway implements careful resource management to prevent resource exhaustion:

  1. Memory Management
  2. Response size limits based on client tier
  3. Streaming buffer size limits
  4. Off-heap buffers for large responses

  5. Garbage collection tuning for predictable latency

  6. Connection Management

  7. HTTP connection pooling (default: 100 per route)
  8. Connection TTL: 5 minutes
  9. Idle timeout: 60 seconds

  10. DNS cache TTL: 30 seconds

  11. Monitoring and Adaptation

  12. Real-time resource usage monitoring
  13. Adaptive concurrency limits based on system load
  14. Graceful degradation under high load
  15. Health check probes for external dependencies
